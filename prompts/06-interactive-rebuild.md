# Промт 06 — пересборка статических страниц в полноценный сайт

> Инструкция для агента. Цель: превратить пиксель-точный, но статичный вывод
> Figma-кодогена в рабочий сайт с интерактивом (слайдеры, варианты выбора,
> аккордеоны, формы, модалки), не теряя визуального паритета с макетом.
> Файл универсален: конкретика сайта — только в блоке «Привязка» ниже.
> После применения этого промта все последующие правки по указке владельца
> записываются в «Журнал доработок» в конце файла (append-only).

## 1. Исходная ситуация (читать перед работой)

Сборка — SSG-сайт из пиксельного кодогена: каждый маршрут уже содержит готовый HTML,
React гидратирует его (`hydrateRoot`), а «интерактивные» элементы пока являются
статичными состояниями (открытый/закрытый аккордеон, кадр 1/2/3 слайдера, выбранный
вариант карточки). Поэтому:

- Минифицированный бандл НЕ редактируется никогда. Работа идёт поверх SSG DOM
  (progressive enhancement) отдельными ES-модулями; hydration не отключается.
- Источник визуальной истины — `reference/`. Источник интерактивных состояний —
  QA-копии `fixtures.html`/`structure.html` в reference: там собраны состояния
  компонентов. Поведение строим так, чтобы в каждом состоянии виджет совпадал с
  соответствующим кадром фикстуры. QA-страницы в публикацию не входят.
- Состояний, которых нет в фикстурах, макет не содержит: их поведение и вид
  согласуются с владельцем И фиксируются в Журнале доработок (раздел «H»).
  Самовольно не изобретать.

## 1a. Текущая архитектура Syntonia (важно)

- SSG: `site/scripts/ssg.mjs`; на странице есть `data-prerendered="true"` и `data-route`.
- Hydration: `site/src/main.jsx` (`hydrateRoot` для непустого root).
- Публикация: `syntonia-site` содержит готовый SSG-вывод; QA-страницы исключены.
- Ворота: `npm run ci:publish` в pipeline, `publish-pixel`, `publish-hydration`,
  `publish-size`; live — GitHub Pages.
- Enhancement-модули: `syntonia-site/assets/interactive/*.js`, подключаются к страницам
  как `<script type="module">`; не переписывают бандл и не отключают hydration.

## 2. Целевое состояние (definition of done для всего сайта)

1. Каждый маршрут открывается и рендерит своё содержимое (не 404-заглушку).
2. Все «картиночные» виджеты работают: клики, клавиатура, состояния.
3. Навигация между страницами — внутренними ссылками без перезагрузок там,
   где это SPA-аналог, иначе корректными переходами; мёртвых ссылок нет.
4. Формы валидируются и уходят в осмысленный финал (stub-эндпоинт + thanks),
   пока нет реального бэкенда — заглушка честно помечена в Журнале.
5. Визуальный паритет с эталоном сохранён во всех статичных зонах;
   все отклонения — согласованы и перечислены в Журнале.
6. Проверки зелёные (§8), `site.json`/CHANGELOG обновлены тем же коммитом.

## 3. Принципы

1. **Эталон неприкосновенен.** `reference/**` — read-only, точка сравнения.
2. **Паритет по умолчанию.** Первое состояние виджета должно совпадать с
   эталоном пиксельно; отклонения — только из списка согласованных.
3. **Реальное поведение вместо кадров.** Кадры слайдера в вёрстке — не
   «три дива», а один слайдер с тремя слайдами. Статик-дубли состояний
   после внедрения живого виджета удаляются из рабочей копии.
4. **Прогрессивное улучшение.** Базовая разметка/контент доступны без JS;
   интерактив — поверх через отдельные ES-модули.
5. **Один виджет — один источник.** Логику не размазывать по inline-обработчикам;
   код — в `assets/interactive/`, стили-слой — в `assets/interactive.css`.
6. **Готово = проверка + запись.** «Работает при мне» не засчитывается:
   чеклист §8 пройден, `site.json` обновлён, запись в Журнале добавлена.

## 4. Карта кода рабочей копии

```
/assets/interactive/          — ES-модули интерактива (по модулю на паттерн)
    slider.js, accordion.js, tabs.js, chooser.js, quiz.js,
    modal.js, forms.js, nav.js, menu.js, theme.js, ...
/assets/interactive.css       — слой стилей интерактива (поверх basic.css)
/scripts/…                    — существующие служебные скрипты (не ломать)
work/<page>-plan.md           — план по странице (создаётся в §5.1)
work/<page>-verify.md         — заполненный чеклист §8 по странице
```

На каждую страницу шелл дополнительно подключает только нужные модули:
`<script type="module" src="./assets/interactive/slider.js">` и т.д.

## 5. Порядок работы

### 5.1. Инвентаризация (перед первой правкой, один заход на страницу)

1. Открыть эталон страницы и её кадры/компоненты в fixtures/structure.
2. Составить `work/<page>-plan.md`: таблица «зона → статичный артефакт →
   кадры состояний в фикстурах → паттерн из §6 → приоритет (P1 навигация/
   контент, P2 интерактив, P3 украшения)».
3. Сверить с §10 (готовый инвентарь, если есть) и дополнить его находками.

### 5.2. Реализация по паттернам §6

- Работать строго по одному паттерну за итерацию; после каждого — локальная
  проверка страницы (`scripts/serve`), консоль без ошибок.
- Состояние верстать по кадрам фикстур: размеры, отступы, иконки состояний —
  из кадра; переключение — классом/атрибутом (`data-state`), не inline-стилями.
- Анимации — короткие (≤300 мс), по `transform`/`opacity`; обязательно
  `@media (prefers-reduced-motion: reduce)` — мгновенное переключение.

### 5.3. Приёмка страницы

Пройти §8 целиком → заполнить `work/<page>-verify.md` → обновить
`site.json` (`status: accepted`, note со списком внедрённых паттернов) →
CHANGELOG → фиксация в Журнале доработок (§9) → коммит.

### 5.4. Новая выгрузка из конвейера (sync)

Не перезаписывать рабочую копию. Порядок: новый `reference/<id>` → повторный
прогон pixel-0 для непринятых страниц → страницы `accepted` обновляются только
переносом известных доработок из Журнала (§9 — он и есть список переноса).

## 6. Каталог интерактивных паттернов

Для каждого: как распознать в статике, эталон поведения, требования, готовность.

### 6.1. Слайдер / карусель
- Признаки: серия одинаковых кадров со стрелками, иконки `slider-arrow*`,
  состояния пагинации/точек в фикстурах.
- Поведение: свайп/клики стрелок/клавиши ←→; цикл — как в фикстурах
  (если последний кадр существует с задизейбленной стрелкой — без зацикливания);
  автоплей только если виден в фикстурах, иначе нет.
- Требования: `role="region" aria-roledescription="carousel"`, кнопки с
  `aria-label`, текущий слайд — `aria-current`; контент слайдов в DOM сразу
  (SEO), без layout shift; lazy-загрузка изображений вне первого слайда.
- Готово: 3 кадра фикстуры воспроизводятся состояниями живого слайдера
  визуально идентично; работает мышь+клавиатура+тач.

### 6.2. Аккордеон / FAQ
- Признаки: пары кадров «вопрос закрыт/открыт», иконка `accordeon*`, стрелка.
- Поведение: клик по заголовку раскрывает; режим — один-открытый или
  мульти — по фикстурам (если есть кадр с двумя открытыми — мульти).
- Требования: `<button aria-expanded>` + регион; высота анимируется по
  `grid-template-rows`/max-height без прыжков; свёрнутый контент остаётся
  в DOM (SEO), скрыт `hidden` после анимации.
- Готово: открытие/закрытие совпадает с кадрами; клавиатура (Enter/Space).

### 6.3. Варианты выбора (карточки-опции, тарифы, форматы)
- Признаки: кадры одинаковой карточки в состояниях Default/Active
  (`option-check`, `state-active/default` в ассетах).
- Поведение: одиночный выбор (radio-семантика) или множественный — по
  фикстурам; выбор меняет связанную зону (цена/описание) — если связь видна
  в кадрах, иначе только визуальное состояние + фиксация «связь не задана»
  в Журнале как вопрос владельцу.
- Требования: fieldset/legend или `role="radiogroup"`; выбор доступен
  с клавиатуры; состояние не теряется при rerender.
- Готово: состояния совпадают с кадрами; выбранное значение доступно
  скрипту формы (data-атрибут), а не только глазу.

### 6.4. Квиз / многошаговая форма
- Признаки: страница quiz + кадры шагов, `option-check`, прогресс, результат.
- Поведение: шаги по экранной цепочке фикстур; назад/вперёд; результат —
  по правилам видимым в кадре результата; без сети.
- Требования: один шаг в DOM-видимости, остальные `hidden`; фокус на
  заголовок шага при переходе; `aria-live="polite"` на прогрессе.
- Готово: полный проход клавиатурой; состояние восстанавливается при
  возврате на шаг; кадр результата совпадает визуально.

### 6.5. Формы (заявка, бронирование, checkout)
- Признаки: поля без action, кнопка «пока не работает», thanks-страницы.
- Поведение: клиентская валидация (обязательные, формат), ошибки у полей
  по состояниям фикстур; успех → переход на соответствующую thanks-страницу;
  отправка — через `FORMS_ENDPOINT` (пока stub: сохранение в localStorage +
  вывод payload в консоль/страницу-отладку). Не имитировать «отправлено»
  без сохранения данных — это обман, фиксируется в Журнале отдельно.
- Требования: label у каждого поля, `aria-invalid`/`aria-describedby` на
  ошибках, submit по Enter, блокировка двойного submit, телефон/дата — маска
  только если есть в фикстурах.
- Готово: невалидная форма показывает ошибки по кадрам; валидная → thanks;
  payload сохраняется и читаем.

### 6.6. Модалки / поповеры
- Признаки: кадры с затемнением, `modal-close`, состояния открытого окна.
- Поведение: открытие из триггеров, закрытие по Esc/крестику/клику на фон
  (если фон кликабелен в макете); возврат фокуса в триггер.
- Требования: `role="dialog" aria-modal`, фокус-трап, блокировка скролла
  фона без сдвига (компенсация scrollbar).
- Готово: кадры открытого состояния совпадают; цикл фокуса проверен.

### 6.7. Меню / навигация шапки
- Признаки: `nav-icon`, состояния пунктов, дропдауны, `btn-login`.
- Поведение: hover-и active-состояния из фикстур; текущая страница подсвечена;
  выпадающие списки — по hover И клику/фокусу (не hover-only).
- Требования: `aria-current="page"`; дропдауны закрываются по Esc и
  focus-out; навигация работает с клавиатуры целиком.
- Готово: пройдена вся шапка клавиатурой без «провалов».

### 6.8. Якорные ссылки и длинные страницы
- Поведение: плавный скролл (off при reduced-motion), компенсация высоты
  sticky-шапки (`scroll-margin-top`), подсветка активного раздела TOC
  (`toc-group-icon` в ассетах) — scrollspy по фикстурам.
- Готово: каждый якорь ведёт к видимому заголовку без перекрытия шапкой.

### 6.9. Медиа-обложки (video/player)
- Признаки: `play`, `watch`, обложки с кнопкой.
- Поведение: до наличия реального видео — заглушка-поведение согласуется
  (модалка «видео появится» или скрытие триггера); кадр с плеером из фикстур —
  целевое открытое состояние.
- Готово: клик не ведёт в пустоту; состояние соответствует кадру.

### 6.10. Тема / переключатели (если есть `theme-dark/light`)
- Только если присутствует в фикстурах: переключатель, выбор сохраняется
  в localStorage, начальное — из `prefers-color-scheme` (или фиксированное,
  как в макете), без FOUC (класс ставится до рендера, inline-скрипт в head
  шелла — это ЕДИНСТВЕННОЕ разрешённое место inline-скрипта).

### 6.11. Служебные страницы
- 404: живая навигация обратно (не тупик); ссылка «на главную».
- thanks-*: понятный следующий шаг; уникальные заголовки.
- legal-*, account-*: если контента нет — пометка «ожидает контент от
  владельца» в теле страницы И в Журнале; не оставлять рендерящуюся
  404-заглушку под осмысленным именем файла.

## 7. Запреты

- Не редактировать `reference/**`, минифицированный бандл сборки, служебные
  `scripts/*` конвейера выгрузки.
- Не изобретать состояния/секции/тексты, которых нет в макете и фикстурах,
  без записи-вопроса в Журнал (см. «изобретённое» в конвейере).
- Не править визуал статичных зон: отступы, типографика, цвет — из токенов
  и кадров; несогласованное «улучшение дизайна» — дефект приёмки.
- Не добавлять внешние CDN/трекеры/шрифты без явной указки владельца.
- Не создавать новые страницы-оболочки без маршрута в бандле или без
  переноса содержимого в статичный HTML (иначе — заглушка 404 под красивым
  именем).

## 8. Проверки (ворота страницы и релиза)

Каждая страница перед `accepted`:
1. Рендер: все маршруты открываются, у каждой страницы осмысленный `<title>`;
   ни один маршрут не показывает 404-компонент.
2. Консоль: нет ошибок/404 ресурсов на всех страницах.
3. Клавиатура: весь интерактив достижим и управляем; фокус виден.
4. Ссылки: обход всех внутренних ссылок → 0 ведущих в `/404`/`#`/пустоту,
   кроме честно помеченных в Журнале.
5. Соответствие: состояния виджетов сверены с кадрами фикстур (по чеклисту
   `work/<page>-verify.md`); статичные зоны — визуально с эталоном.
6. Производительность: нет новых дублей ассетов; изображения >300 КБ — только
   если так в эталоне; первый экран без новых тяжёлых зависимостей.
7. `site.json` и CHANGELOG обновлены тем же коммитом; Журнал дополнен.

Релиз (весь сайт): повтор всех ворот + `prepare-pages` + проверка на
опубликованном URL + тег версии (semver: контент/интерактив — minor,
правки — patch; несовместимая смена структуры — major с записью в Журнале).

Baseline Stage 3 — тег `stage3-baseline` (v0.5.0). После изменений используем
`npm run publish:prepare` / `ci:publish` (m3 pixel/hydration). Для страниц в статусе
`baseline` pixel-0 обязателен; для переделанных страниц расхождения допустимы только
при записи в журнале и скриншотах в `work/<page>-verify.md`.

## 9. Журнал доработок (append-only — правила ведения)

Назначение: повторяемость. Всё, что агент сделал по указке владельца после
применения основного промта, записывается сюда; при новой выгрузке из
конвейера и при применении к похожему сайту журнал — это список переноса.

Правила записи:
- Одна запись = одна указка владельца (или один пакет мелких правок за сессию).
- Пишется ТЕМ ЖЕ коммитом, что и сама правка; самое новое — СНИЗУ файла.
- Записи не редактируются и не удаляются; отмена — новой записью «отменено в N».
- Поля: ID, дата, указка (дословно или близко), что сделано, затронутые
  файлы/зоны, тип (`правка`|`новое поведение`|`отклонение от макета`|
  `вопрос-ответ`|`отмена`), проверка (как проверено), статус.
- Вопросы владельцу без ответа — тип `вопрос-ответ`, статус `ожидает`.
- Отклонение от макета без записи = нарушение, приёмка страницы не считается.

Шаблон записи:

| ID | Дата | Указка | Что сделано | Файлы/зоны | Тип | Проверка | Статус |
|----|------|--------|-------------|-----------|-----|----------|--------|
| D-001 | ГГГГ-ММ-ДД | … | … | … | правка | … | done |
